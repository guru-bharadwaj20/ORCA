# Contributing to ORCA

Thanks for working on ORCA. This page is the one-stop orientation: how to get set up,
the ground rules for a change, and the **project roadmap** so you can see what's done,
what's underway, and what's free to pick up.

## Getting set up

```bash
npm install
npm run build        # tsc + copy templates into dist/
npm test             # vitest (hermetic — no keys, no Docker)
npm run lint
npm run typecheck
npm run format:check
```

ESM-only TypeScript with `NodeNext` resolution; intra-project imports use explicit `.js`
extensions. The repo is an npm-workspaces monorepo — the root package is the publishable
`orca-agent-cli`, and `vscode-extension/` consumes it through its subpath exports.

## Ground rules

- **Green before every push.** `typecheck`, `lint`, `format:check`, and the full test
  suite must all pass. Tests stay hermetic (temp-dir fixtures, injected AI facade — no
  network, no Docker, no VS Code).
- **Small, focused PRs.** One coherent unit per branch; branch off `main`, open a PR.
  With several people active, PRs (not direct-to-`main` pushes) keep everyone's work
  from colliding.
- **Adding a stack is adding data, not editing an enum.** New frameworks/ecosystems land
  as a `BuildRecipe` + matcher + test, never as new control flow. See
  [`docs/universal-understanding-plan.md`](docs/universal-understanding-plan.md).
- **Commit messages:** short (4–6 words), a conventional prefix
  (`feat:`/`fix:`/`chore:`/`test:`/`refactor:`/`docs:`), written like an engineer wrote
  them.

### Architectural debt — verified, prioritized

These are **confirmed** findings from a codebase review (not speculative improvements):
each one was traced to specific code and is reproducible today. They are tracked
separately from the feature list above because they are _structural_ — the new
architecture (Phases A–F) was largely built **alongside** the old path rather than
replacing it, so both are live simultaneously.

Priority means impact on the north star ("give ORCA any repository"), not effort.
**P0 blocks universal understanding today; P1 is decision #1 left unfinished; P2 is
robustness.** Work them roughly in order — P0 makes P1 substantially easier, and the two
share a blast radius, so pairing them is reasonable.

### Audit fixes — landed

A full-codebase audit (2026-07-25) produced these; each was verified by execution, not
inspection alone, and each shipped with regression tests.

| Stub | Pri | Fix                                                                                                                                                                                                                                                                                       |
| :--: | :-: | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
|  🟢  | P0  | **`.env` injection.** A newline in the AI-supplied `reason`/`value` escaped its line and injected a live variable (confirmed: `INJECTED_ADMIN=true`). Normalized at the schema boundary (`singleLine`) and again in `buildEnvFile`, so the format is safe for any caller.                 |

**All audit findings are now closed**, including the two follow-on halves that were
outstanding: evidence adoption in the user-facing detectors, and cache adoption across
detection (solved with an ambient run scope instead of the threaded parameter originally
planned — same guarantee, no signature churn). See the P1/P2 rows above for scope and the
one deliberate exclusion.

**Note on probing.** None of the above needs dynamic execution. ORCA currently drops
services it has _already successfully detected_ — a limit of the plan layer's shape, not
of static analysis. P0–P1 containerize materially more repos than a tier-4 prober would,
at zero security cost. This is the evidence for keeping decision #2 deferred.
