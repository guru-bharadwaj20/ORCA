# Contributing to ORCA

Thanks for working on ORCA. This page is the one-stop orientation: how to get set up,
the ground rules for a change, and the **project roadmap** so you can see what's done,
what's underway, and what's free to pick up.

## Getting set up

```bash
npm install
npm run build        # tsc + copy templates into dist/
npm test             # vitest (hermetic — no keys, no Docker)
npm run lint
npm run typecheck
npm run format:check
```

ESM-only TypeScript with `NodeNext` resolution; intra-project imports use explicit `.js`
extensions. The repo is an npm-workspaces monorepo — the root package is the publishable
`orca-agent-cli`, and `vscode-extension/` consumes it through its subpath exports.

## Ground rules

- **Green before every push.** `typecheck`, `lint`, `format:check`, and the full test
  suite must all pass. Tests stay hermetic (temp-dir fixtures, injected AI facade — no
  network, no Docker, no VS Code).
- **Small, focused PRs.** One coherent unit per branch; branch off `main`, open a PR.
  With several people active, PRs (not direct-to-`main` pushes) keep everyone's work
  from colliding.
- **Adding a stack is adding data, not editing an enum.** New frameworks/ecosystems land
  as a `BuildRecipe` + matcher + test, never as new control flow. See
  [`docs/universal-understanding-plan.md`](docs/universal-understanding-plan.md).
- **Commit messages:** short (4–6 words), a conventional prefix
  (`feat:`/`fix:`/`chore:`/`test:`/`refactor:`/`docs:`), written like an engineer wrote
  them.

### Audit — framework taxonomy pass

Findings from auditing the taxonomy work itself, all fixed. Recorded because three of the
four were **invisible in the tests that existed** and only surfaced by probing real
manifests or sweeping every fixture for double-placement.

| Fix                                         | What was wrong                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| :------------------------------------------ | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Defer list swallowed its own frameworks** | `MORE_SPECIFIC_NODE_MARKERS` was derived from `NODE_FRAMEWORK_RECIPES`, so adding `fastify`/`koa`/`hapi` recipes made the seed detector _defer_ to exactly the frameworks it had just learned to name — all three silently returned `'unknown'` again. "Defer to a more specific recipe" now means "a framework this detector cannot name", computed by subtracting the seed tables.                                                                                                                                                                                                                                                                                                                                                                              |
| **Detected entrypoint ignored**             | `dockerfileVarsFor` used `recipe.startCommand` unconditionally, so `component.entrypoint` — resolved by `detectEntrypoint`, evidence-backed at 0.85, surfaced in the reasoning trail — never reached the Dockerfile. For frameworks that ship no CLI (fastify/koa/hapi/hono) the hardcoded `npm run start` was pure guesswork and died on any repo whose script is `dev` or `serve`. Those recipes now declare `startCommand: ''` and `startCommandFor` resolves recipe → detected → convention, mirroring `withStartCommand` on the ecosystem path.                                                                                                                                                                                                              |
| **Port scan leaked across components**      | The ROOT CAUSE beneath the phantom, found by chasing why `libraryDetector` never fired. `portsFromCode` walks recursively, so a monorepo root reported its CHILDREN's ports (`react-express-nodb-repo` → `[5173, 5000]`). Both `detectComponentRole`'s master gate ("declares a port ⇒ it is a service") and `libraryDetector`'s first check read `declaredPorts`, so **no parent directory could ever be classified as anything but a service**. A scan now stops at any subdirectory with its own manifest — that is a different component and its ports belong to it.                                                                                                                                                                                          |
| **Phantom service on workspace roots**      | The bare fallback matches on a manifest ALONE, so a monorepo root holding only `{ "private": true, "workspaces": [...] }` was placed as a service running `npm start` in a directory with nothing to start — beside the real components from its own workspaces. Found by sweeping every fixture for double-placement, not by a failing test. Now suppressed by ROLE rather than by a workspace special case: a bare fallback carries no evidence the directory runs anything, so when the role detectors independently say `library` (no bin, no start script, no entry module) the two signals disagree and nothing is placed — which covers Go/Rust/Python library shapes too. A FRAMEWORK recipe still places, since matching one requires real dependencies. |
| **Duplicate `python-app` definition**       | The recipe existed twice, byte-identical, one registered and one for `recipeForComponent` — exactly the setup where one gets edited and the other does not. Now read off the registered entry.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |

Two invariants are now permanent tests rather than manual checks: naming a framework must
never DOWNGRADE its build (a framework the detector can name but
`SEED_RECIPE_BY_FRAMEWORK` does not map falls to the bare fallback and silently loses its
build step), and a blank `startCommand` is allow-listed to the recipes where blank
genuinely means "ask the repo".

### Audit — what the grader made of the leftovers

One further finding, from the tail of the workspace-root work above.

| Fix                                         | What was wrong                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| :------------------------------------------ | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A library graded as a dropped component** | Suppressing the phantom left a warning behind: a root nothing was placed for still got `unplaced-component`, and `assessUnderstanding` grades every one of those as "the generated stack is incomplete". So a monorepo ORCA understood COMPLETELY — every real component placed, the parents correctly recognized as libraries — came out `partial` with `shouldEscalate: true` and spent a tier-3 inference call on a `{ private, workspaces }` file. **Every monorepo fixture in the suite did this**, from the day the suppression landed, because their tests assert PLACEMENT and placement was right the whole time. Those roots are recorded in `insights.unrunnableRoots` and surface as `library-component` instead; `unplaced-component` keeps its meaning and keeps escalating. |

The lesson worth keeping: **"placed nothing" and "could not place" are different
outcomes**, and any signal that collapses them will eventually be graded as a failure.

### Architectural debt — verified, prioritized

separately from the feature list above because they are _structural_ — the new
architecture (Phases A–F) was largely built **alongside** the old path rather than
replacing it, so both are live simultaneously.

Priority means impact on the north star ("give ORCA any repository"), not effort. **P0
blocks universal understanding today; P1 is a correctness or honesty defect; P2 is
robustness.** Work them roughly in order.

**All audit findings are now closed**, including the two follow-on halves that were
outstanding: evidence adoption in the user-facing detectors, and cache adoption across
detection (solved with an ambient run scope instead of the threaded parameter originally
planned — same guarantee, no signature churn). See the P1/P2 rows above for scope and the

**Note on probing.** None of the above needed dynamic execution. ORCA was dropping
services it had _already successfully detected_ — a limit of the plan layer's shape, not
of static analysis. P0–P1 containerized materially more repos than a tier-4 prober would,
at zero security cost. Probing now exists (`src/probe/`) and satisfies its security
contract, but that finding is precisely why it ships **off by default**: it corroborates a
plan the static tiers already built, and is not what makes a repo buildable.
